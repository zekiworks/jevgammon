## 1. `merge/merge_coupled.sh --rollback`: the same paired-update safety as the merge

- **Pre-check, before either reset:**
  - both targets must be commits of their repository (`rev-parse --verify <x>^{commit}`);
  - the target decision.py pin must equal the sha256 of the target chat improve.py.
  - Otherwise nothing is reset (exit 2).
- **Order and compensation:** decision reset, then chat reset. If the chat reset fails, the decision checkout is restored to the head it had before the rollback (exit 3).
- **Post-check:** the working fence pin must equal the chat file. If not, both are restored to the heads before the rollback (exit 4).
- **End state:** every failure path ends with one `STATE:` line giving both heads and whether fence and file agree.
- **Merge path:** its failure paths now use the same `restore` + `STATE` too.
- **Test hooks:** `MC_FAIL_SECOND=1` fails the second update (merge or reset). `MC_BREAK_AFTER=1` changes the chat file after both updates, so the post-check sees a pin mismatch.
- **Tests:** `test_merge_coupled.sh` on throwaway shared clones under ~/.cache, **15/15 PASS** (`merge/test_merge_coupled-output.txt`). Failed paths:

| Path | Exit | Result |
|---|---|---|

| merge: pin mismatch after both merges | 4 | restored, STATE agrees |
| rollback to an unknown commit | 2 | refused, nothing reset |
| rollback targets that disagree (old chat + new pin) | 2 | refused, nothing reset |
| rollback: second reset fails | 3 | decision restored, STATE agrees |

  Plus the happy merge and rollback, and the tracked tree clean at the end.

## 2. `v3-players/v3_players.py`: foreign keys on, one guarded transaction

- **Connections:** every connection is made by `connect()` with `PRAGMA foreign_keys = ON`.
- **Guarded transaction:** insert and rollback each run as ONE transaction opened with `BEGIN IMMEDIATE`, which takes the write lock before the first check. It refuses if foreign keys are off or a transaction is already open.
  - **insert:** the plan (name absent / identical / conflict) is made inside the lock.
  - **rollback:** identity check, reference re-check and deletes all happen inside the lock. Each DELETE is by recorded id AND name, must touch exactly 1 row, and the whole transaction is rolled back on any refusal.
  - Only the manifest's ids are read or deleted, so no other row is touched (pre-existing rows, the running Gemma 4 E4B (on)).
- **Tests:** `test_v3_players.py` **9 OK** (`test_v3_players-output.txt`; scratch DBs with v3.db's schema and foreign keys on). New:
  - foreign keys off → refused;
  - another connection trying to reference a recorded row while rollback holds the lock gets `database is locked`; after the commit, a late reference is refused by the foreign key;
  - the engine itself refuses deleting a referenced row.
